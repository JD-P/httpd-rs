# Verus proof strategies

This page inventories every explicit `proof fn` in [`crates/verified/src/lib.rs`](../crates/verified/src/lib.rs). It names the component, states the claimed property in plain language, identifies the proof's real epistemic basis, and gives a deliberately skeptical review-confidence score.

The unit of inventory is a named Verus theorem or lemma, not every function for which Verus generates a verification condition. Executable `fn` bodies prove implementation postconditions and `spec fn` bodies define models; listing those as if each were an independent security theorem would inflate the table and obscure the distinction. The higher-level composition claims, including executable PCRE2 grammar refinement, remain tracked in [`verification-status.json`](verification-status.json).

## How to read the ratings

The score is a maintainer judgment about how likely the *proof strategy and its current implementation* are to survive hostile review, not a Verus pass/fail result:

| Score | Meaning |
| ---: | --- |
| 1–2 | Example-only, measured, or dependency-assumption evidence; useful but not a general proof of the production claim. |
| 3–4 | The arithmetic or logical implication is sound, but the hard part is encoded as an assumed charge, limit, fact, or incomplete model. |
| 5–6 | Exact finite model or case analysis with a material runtime-refinement or coverage seam. |
| 7–8 | General invariant/induction or exact machine algebra with a credible executable refinement; external effects remain trusted. |
| 9–10 | End-to-end refinement through all relevant production state and dependency semantics. No current row earns this. |

A low score does **not** mean Verus failed to prove the stated formula. It means the formula may be easier than the security claim readers could infer from its name. In particular, an admission theorem of the form “if the gate accepted, the declared charge is below the declared limit” does not prove that the charge models actual resource use.

## Strategy definitions

| Basis | What the proof really rests on | Default score |
| --- | --- | ---: |
| Definitional SMT consequence | The proof body is empty or nearly empty. Verus unfolds a small Boolean/enum specification and SMT proves the stated implication. This checks the model's internal consequence, not that the model is complete or that every runtime caller supplies truthful facts. | 4/10 |
| Finite case split over the model | SMT and/or an explicit `match` exhaust the modeled enum/Boolean cases. This is exact for the declared transition or projection, but runtime representation and call-site coverage remain separate obligations. | 6/10 |
| Finite-state invariant/case analysis | The transition relation is a closed enum/record model and Verus proves an invariant, an absorbing state, or a gate-order consequence by exhaustive symbolic cases. Strong within the model; only as strong in production as the executable refinement and event coverage. | 7/10 |
| HTTP/2 executable state-machine refinement | The closed HTTP/2 model is checked across its admitted events and its executable reducers are consumed by the vendored frame, HPACK, stream, counter and flow-control paths. This is strong implementation evidence for those transitions; generated Huffman tables, container library semantics, async scheduling and kernel I/O remain outside the theorem. | 7/10 |
| Structural induction over a mathematical sequence | The body recurses on a decreasing sequence/index and establishes the property for arbitrary length. This is a real unbounded proof of the specification; the remaining risk is whether the executable parser/loop is fully refined to that specification. | 7/10 |
| Structural induction plus executable refinement | The theorem uses induction over arbitrary input and is paired with an executable loop whose postcondition is the same specification. This gives comparatively strong implementation evidence, while allocation, library and OS semantics remain trusted. | 8/10 |
| Exact bit-vector algebra | Verus's bit-vector solver proves the fixed-width mask identity for every input value. This is exact for the operation; the principal remaining question is whether production uses the proved operation at every relevant merge. | 8/10 |
| Exhaustive finite-domain algebra | The proof enumerates a genuinely finite byte/digit domain or composes injective finite encodings. The mathematical claim is exact; production strength still depends on the executable encoder/parser refining the same definitions. | 7/10 |
| Quantified sequence/prefix algebra | Explicit quantified assertions prove the property for arbitrary sequence lengths without testing a finite sample. This is strong for the mathematical path/framing relation; the runtime's construction of those sequences remains the refinement boundary. | 7/10 |
| Admission inequality restatement | The admission predicate already requires an overflow-safe inequality; SMT shows that a successful admission therefore lies under the configured limit. It does not prove that the chosen limit is safe or that the charged quantity equals real CPU, memory or I/O. | 4/10 |
| Estimated/calibrated cost model plus arithmetic | This is, candidly, a charge estimate followed by a proof that the estimated factors multiply or sum to at most the budget. Verus proves the arithmetic, not that the estimate upper-bounds the dependency or all adversarial data shapes. | 3/10 |
| Measured/dependency constants plus arithmetic | Fixed limits were selected from dependency limits and adversarial measurements, then Verus shows those numbers fit the declared envelope. This does not derive a worst case from the dependency implementation and should be treated as a monitored assumption. | 2/10 |
| Concrete examples only | The solver unfolds the recursive matcher for a small hand-picked set of examples. These are useful regression oracles, not a general conformance proof and not evidence that unlisted cases agree with Apache. | 2/10 |

## What this inventory does not prove

The table is intentionally narrower than the overall assurance case. It does not turn a model-only theorem into evidence that all runtime paths call the gate, prove Rust RAII destruction as a Verus heap theorem, derive CPU or allocator worst cases from third-party source, model kernel scheduling/filesystem/network behavior, or establish Apache conformance. Those links are supplied, with varying strength, by executable refinement postconditions, source inventories, fuzzing, integration tests, measured budgets and explicit dependency/kernel assumptions.

The most review-sensitive rows are therefore the score-2 dependency constants and concrete fnmatch oracles, followed by the score-3 regex cost model. A successful adversarial review should try to falsify those empirical/modeling premises before spending time rechecking the elementary SMT implications.
